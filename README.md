# Семейные расходы

Go-сервис учёта семейных расходов: Telegram-бот с инструментами LLM и веб-панель без авторизации. PostgreSQL хранит расходы, историю диалогов и результаты операций. Панель на Go HTML templates, локальном Bootstrap 5.3.8 и обычном JavaScript; все операции с расходами выполняются через REST API.

## Быстрый запуск

Нужны Docker с Compose и интернет для загрузки образов. Для бота также нужны Telegram-токен и API-ключ Groq.

```sh
cp .env.example .env
# Укажите в .env POSTGRES_PASSWORD, TELEGRAM_ALLOWED_USER_IDS и, для бота, токены.
docker compose --env-file .env -f deploy/docker-compose.yaml up --build
```

Команды выполняются из корня репозитория. Файлы Dockerfile и Compose находятся
в `deploy/`; `.env` и `.env.example` остаются в корне. `.dockerignore` также
остаётся в корне, поскольку это контекст сборки Docker. Имя основного проекта
Compose закреплено как `expenses`, чтобы перенос файлов не менял используемый
том `expenses_postgres_data`. Для запуска также доступен `make run`. Команды `make` и `make help` показывают
список доступных задач.

Панель: **http://localhost:8080**. Приложение автоматически применяет SQL-миграции и создаёт участников из allowlist. До первого сообщения боту участник отображается своим Telegram ID. База не публикует порт; данные сохраняются в томе `postgres_data`. `docker compose --env-file .env -f deploy/docker-compose.yaml down` сохраняет данные, `docker compose --env-file .env -f deploy/docker-compose.yaml down -v` удаляет их.

Пароль БД задаётся обязательной переменной `POSTGRES_PASSWORD` в `.env`; приложение получает его через `PGPASSWORD`, отдельно от DSN. Для существующего тома укажите текущий пароль (в прежней конфигурации — `expenses_local`): изменение переменной не меняет пароль уже созданной роли PostgreSQL.

Healthcheck приложения обращается к `/api/users` и проверяет доступность HTTP и запрос к БД. `docker compose --env-file .env -f deploy/docker-compose.yaml up -d --build --wait` дожидается готовности обоих сервисов. Статус `unhealthy` сам по себе не перезапускает контейнер; `restart: unless-stopped` применяется при завершении процесса.

Можно сначала оставить `TELEGRAM_BOT_TOKEN` пустым: панель и API работают без Telegram и LLM. Замените примеры ID реальными перед включением бота. После изменения `.env` выполните `docker compose --env-file .env -f deploy/docker-compose.yaml up -d --build`.

## Получение доступов

1. В Telegram откройте [@BotFather](https://t.me/BotFather), отправьте `/newbot`, задайте имя и username. Скопируйте выданный токен в `TELEGRAM_BOT_TOKEN` локального `.env`.
2. Узнайте числовые Telegram ID участников. Например, участник может обратиться к [@userinfobot](https://t.me/userinfobot). Другой способ: каждый участник пишет вашему новому боту, а вы, **до запуска polling-приложения**, запрашиваете `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и берёте `message.from.id`. Не публикуйте токен и результат с личными данными. Запишите ID через запятую в `TELEGRAM_ALLOWED_USER_IDS`.
3. Создайте аккаунт в [Groq Console](https://console.groq.com/), откройте [API Keys](https://console.groq.com/keys), создайте ключ и внесите его в `LLM_API_KEY`.
4. Выберите доступную вашему аккаунту модель с [tool calling](https://console.groq.com/docs/tool-use/overview). В примере стоит `llama-3.3-70b-versatile`; доступность и бесплатные лимиты зависят от аккаунта и могут меняться. Настройки модели не зашиты в клиент: при необходимости измените `LLM_MODEL` и `LLM_BASE_URL`.
5. Запустите Compose и отправьте боту «кофе 350». Проверьте запись в панели. Второй участник должен писать с собственного аккаунта.

Используется long polling. На один токен запускайте один экземпляр приложения. Если бот раньше использовал webhook, предварительно отключите его методом Telegram `deleteWebhook`. Бот работает только в личных чатах с разрешёнными участниками. Токены, ключи и `.env` не коммитятся.

## Настройки

| Переменная                   | Значение                                                                      |
|------------------------------|-------------------------------------------------------------------------------|
| `TELEGRAM_ALLOWED_USER_IDS`  | Обязательный список положительных числовых ID через запятую                   |
| `TELEGRAM_BOT_TOKEN`         | Токен; пустое значение отключает бота                                         |
| `LLM_BASE_URL`               | OpenAI-совместимый API, по умолчанию `https://api.groq.com/openai/v1`         |
| `LLM_API_KEY`                | Ключ; обязателен при включённом боте                                          |
| `LLM_MODEL`                  | Модель с tool calling; пример `llama-3.3-70b-versatile`                       |
| `LLM_TIMEOUT`                | Общий бюджет запроса агента, по умолчанию `30s`, допустимо `1s`–`2m`          |
| `APP_TIMEZONE`               | Часовой пояс календарных дат; по умолчанию `Europe/Moscow`                    |
| `APP_PORT`                   | Порт панели на localhost в Compose, по умолчанию `8080`                       |
| `POSTGRES_PASSWORD`          | Обязательный пароль БД в Compose; для существующего тома — текущий пароль     |
| `TEST_DB_PORT`               | Порт тестовой БД на localhost; по умолчанию `0` — свободный порт от Docker    |
| `DATABASE_URL`               | DSN при запуске Go вне Compose; внутри Compose устанавливается автоматически  |
| `HTTP_REQUEST_TIMEOUT`      | Таймаут обработки API-запроса; положительная длительность, по умолчанию `5s` |
| `HTTP_ADDR`                  | Адрес Go HTTP-сервера, по умолчанию `:8080`; в Compose фиксирован             |

Панель по условию задания не имеет авторизации и доступна всем, кто может открыть её адрес. Compose публикует её на `127.0.0.1`. Валюта одна — RUB; суммы положительные, комментарий до 1000 символов. PostgreSQL 17, Go 1.26.9+.

## Примеры диалогов

```text
кофе 350
такси 1200 вчера
покажи траты за неделю
сколько потратил на еду в этом месяце
последнее было не 350, а 450
удали такси
вторую
```

«За неделю» означает последние 7 календарных дней, включая сегодня; «в этом месяце» — с первого числа по сегодня. «Последняя трата» сортируется по времени создания, даже если дата расхода в прошлом. Текущая локальная дата передаётся модели.

При нескольких найденных расходах бот должен показать нумерованный список и запросить выбор. Go запрещает неоднозначную мутацию до ответа номером («вторую», «2») или `#ID`. Для одного совпадения обязательного подтверждения нет. В панели удаление подтверждается диалогом браузера. Один запрос создания — один расход; несколько расходов нужно присылать отдельно. Сообщения с несколькими явными `#ID` требуют уточнения одного расхода до поиска и изменения; прежний ожидающий выбор очищается. История, кандидаты и ожидающее действие разделены по участникам и истекают через 30 минут бездействия. Нумерацию найденных расходов формирует Go, поэтому «вторую» относится к тому же списку, который увидел пользователь. Список привязан к update и ID сообщения Telegram; выбор разрешается только после успешной доставки и только для ответа, отправленного после этого сообщения. Недоставленные списки не активируют действие, устаревшие списки отменяются, а терминальная ошибка доставки очищает ожидающий выбор. Для ожидающего действия такой ответ обрабатывается без LLM; новое сообщение с другим запросом отменяет ожидающий выбор. Выбор последнего расхода разрешается только для однозначной полной формулировки, например «удали последний расход» или «последнее было не 350, а 450». Отрицания, исключения и дополнительные условия не дают разрешения на shortcut latest: бот должен выполнить обычный поиск и уточнить выбор.

Подтверждения операций, списки и денежные итоги формирует Go из результатов
инструментов и журнала БД. Обычный текст LLM не показывается как результат:
приложение один раз запрашивает вызов инструмента, затем предлагает уточнить
запрос. Для уточнений модель вызывает `clarify_request` с типом недостающего
поля, а текст вопроса задаёт приложение. Выбор номера после обычного просмотра
только указывает расход и не разрешает мутацию из истории; для изменения или
удаления нужен полный запрос. Неверный номер сохраняет исходный список.
Упрощённый просмотр применяется только к известным категориям, такси и кофе;
месяцы и другие временные выражения передаются модели для разбора периода.

Go определяет разрешённый тип операции по текущему запросу: запрос просмотра
не даёт права на запись, а изменение даты не разрешает менять сумму или удалять
расход. Модели передаётся ограниченный набор инструментов; те же ограничения
повторно проверяются перед выполнением. Неоднозначное намерение требует
уточнения. Старые ожидающие действия без проверки намерения после обновления
остаются доступны только как список: для мутации нужно повторить полный запрос.

Уточнения сохраняются в БД: «кофе» → запрос суммы → «350,50» продолжает создание,
а не выбор номера. Отмена и новый явный запрос сбрасывают уточнение. Для прямых
мутаций поддержаны проверенные словоформы, например «аренду» → «аренда»;
остальные описания разбирает модель. Точность прежней суммы проверяется по
полному числу, без обрезания дробной части.

## REST API

| Метод   | Путь                  | Результат                                                             |
|---------|-----------------------|-----------------------------------------------------------------------|
| GET     | `/api/users`          | `{ "items": [{ "id": "101", "name": "Анна", "username": "anna" }] }`  |
| GET     | `/api/expenses`       | `{ "items": [...], "total": 2, "total_amount": "155000" }`            |
| POST    | `/api/expenses`       | `201`, созданный расход                                               |
| PATCH   | `/api/expenses/{id}`  | `200`, изменённый расход; `409` при конфликте версии                  |
| DELETE  | `/api/expenses/{id}`  | `204`, без тела                                                       |

Фильтры списка: `user_id`, `category`, `date_from`, `date_to`, `limit` (1–100, по умолчанию 20), `offset` (от 0). Границы дат включены. Сортировка `spent_at DESC, id DESC`. `total` и `total_amount` относятся ко всему фильтру, независимо от страницы; список и агрегат читаются в одном снимке БД.

**Все ID и денежные значения в JSON — десятичные строки.** `amount` и `total_amount` означают **целые копейки**, `"35050"` = 350,50 ₽. Это сохраняет точность `BIGINT` в JavaScript. `total`, `limit` и `offset` — JSON-числа. Инструменты LLM принимают `amount_rubles` строкой **рублей**, например `"350.50"`. Преобразование выполняется без `float64` и округления, переполнение проверяется в том числе для итогов.

Создание (`Content-Type: application/json`):

```json
{
  "user_id": "101",
  "amount": "35050",
  "category": "еда",
  "spent_at": "2026-10-17",
  "comment": "кофе"
}
```

Ответ содержит те же поля и `id`, `created_at`, `updated_at`, `version`. Версия — десятичная строка, начинается с `"1"` и увеличивается при изменении. `spent_at` — календарная дата `YYYY-MM-DD` без UTC-преобразования. Технические timestamps — RFC 3339 UTC. Категории: `еда`, `транспорт`, `жильё`, `развлечения`, `здоровье`, `покупки`, `другое`.

PATCH изменяет только `amount`, `category`, `spent_at`, `comment`. Пропущенное поле сохраняет прежнее значение; `"comment": ""` очищает комментарий. Владелец существующей записи не меняется. Пустой PATCH отклоняется.

Дополнительное поле `expected_version` задаёт условие изменения, например
`{"comment":"новый","expected_version":"3"}`. Если запись уже имеет другую
версию, API возвращает `409`, не изменяя данные. Для совместимости PATCH без
`expected_version` остаётся безусловным. Панель всегда передаёт исходную версию
и только изменённые поля; при конфликте сохраняет ввод и предлагает заново
открыть запись. Новые расходы получают версию `1`.

SQL-операции API ограничены контекстом запроса с таймаутом `HTTP_REQUEST_TIMEOUT` (по умолчанию 5 секунд). Мутации выполняются в явной транзакции, чтобы отменённый до коммита запрос не завершился позднее в autocommit. Превышение дедлайна возвращает `504`.

Ошибки `400`, `404`, `409`, `500`, `504` имеют формат:

```json
{"error":{"message":"описание ошибки"}}
```

Сообщение выбирается по типу ошибки; исходный текст `err.Error()` клиенту не передаётся.

Запросы ограничены 16 KiB; неизвестные JSON-поля и числовые ID/amount отклоняются. Мутации с чужим `Origin` отклоняются с `403`. API панели административный: бот его не использует, а обращается к сервису с доверенным ID владельца.

Нулевой символ и некорректный UTF-8 отклоняются до SQL как ошибка входа.
Известные постоянные ошибки формата данных не считаются временным сбоем БД.
Неопределённый результат коммита и ошибки соединения сохраняют повторную
обработку с проверкой журнала операций. Непригодный контекст сбрасывается,
а подтверждённый результат операции сохраняется для ответа пользователю.

## Архитектура и гарантии

```text
Telegram → private chat + allowlist → агент → проверка инструментов ┐
                                                                  ├→ expensesvc → PostgreSQL
Браузер → HTML / JavaScript → REST API панели ──────────────────────┘
Telegram → сессии, обработанные update и доставка ───────────────────────────────→ PostgreSQL
```

- `cmd/main.go` — конфигурация, общий процесс, graceful shutdown.
- `internal/expense` — модель, точные деньги, валидация и типизированные команды; без JSON-тегов.
- `internal/expensesvc` — единая точка нормализации фильтров и вызова доменной валидации расходов для REST API и агента. Административный CRUD панели и журналируемые операции бота сохраняют прежние права.
- `internal/expensewire` — DTO для прежнего JSON-контракта API, результатов инструментов и сохранённых сессий: ID, суммы и версии остаются строками.
- `internal/postgres` — отдельные файлы для подключения/миграций, пользователей, CRUD расходов, сессий, update, доставки и журнала операций. Чтение использует `sqlx` (`GetContext` и `SelectContext`) поверх драйвера `pgx`. Транзакции и проверка владельца остаются в хранилище. SQL списка расходов вынесен в `queries.go`, структуры с `db`-тегами и обработка `NULL` — в `rows.go`. Результаты операций формируются типизированными структурами с прежним JSON-форматом.
- `internal/httpapi` — REST API и встроенные HTML/static файлы.
- `internal/agent` — подготовка запроса (`request.go`), детерминированный диалог (`workflow.go`), ограниченный цикл LLM (`model.go`), проверка и выполнение инструментов (`execution.go`), совместимая сериализация сессий и клиент провайдера. `Reply` координирует восстановление и эти этапы.
- `internal/telegram` — polling, allowlist, дедупликация и доставка.
- `internal/botstate` — тип сохранённого ответа для очереди доставки.

HTTP и агент разбирают входные данные и проверяют правила своего канала: JSON, аргументы инструментов, намерение пользователя и выбор кандидата. Нормализация фильтров и валидация данных расходов выполняются в `expensesvc`; PostgreSQL получает подготовленные данные и сохраняет проверки владельца, ограничения БД и транзакции. Для журналируемой операции хранилище сначала ищет результат под транзакционной блокировкой и только при его отсутствии вызывает функцию подготовки и валидации команды из сервиса. Проверка черновика перед сохранением выбора также проходит через сервис.

Модель не получает SQL, административные функции или параметр `user_id`. Чтение бота всегда ограничено владельцем, UPDATE/DELETE проверяют владельца в SQL. Для изменения/удаления нужен ID из ранее найденных кандидатов; чужой или выдуманный ID не проходит. При упоминании прежней суммы она проверяется; UPDATE также проверяет её в БД, чтобы не затереть параллельное изменение.

Агент ограничен 6 шагами, размером истории, ответа и общим таймаутом. `429` и `5xx` повторяются не более двух раз с учётом `Retry-After`, в пределах общего бюджета; ожидание более 10 секунд возвращает ошибку. В логи выводятся безопасные диагностические поля: update ID, операция, категория ошибки, HTTP-код, количество попыток и длительность. Ключи, URL с токенами, тела ответов провайдера и полный текст диалога не логируются.

Один polling-процесс получает пакет до 20 update. Разные участники внутри пакета обрабатываются параллельно, сообщения одного участника — последовательно. Следующий polling и повтор доставки начинаются после завершения всех обработчиков пакета, поэтому подтверждение доставки не гоняется с изменением сессии. При ошибке оставшиеся сообщения этого участника ждут повтора; другие участники завершают обработку. Offset продвигается только через непрерывную последовательность успешно обработанных update. Уже завершённые update после первой ошибки при повторном получении пропускаются по сохранённому состоянию. `telegram_updates.update_id` уникален; изменение и его результат сохраняются атомарно в `expense_operations`, ключ — update и единственный слот мутации. После сбоя доставки используется сохранённый ответ, без нового вызова LLM. После сбоя между мутацией и сохранением ответа результат из журнала проверяется до вызова LLM, нового поиска и валидации старой суммы. Ошибка чтения журнала или неопределённый результат обращения к хранилищу оставляют update доступным для повторной обработки. Повторная отправка пользователем того же текста с новым update создаёт новый расход. Если финальный ответ LLM не получен, бот показывает подтверждённый результат выполненной операции.

Ответ сохраняется в PostgreSQL до подтверждения update. Ошибки доставки не удерживают polling offset: временные ошибки получают `retry_at`, учитывающий Telegram `retry_after`, а постоянные отклонения (`400`, `403`) сразу переводят доставку в `failed`. После трёх неуспешных попыток временная ошибка тоже становится терминальной. Очередь проверяется между polling-запросами; повтор выполняется не раньше `retry_at`, но может задержаться на время long polling. Отправка повторно использует сохранённый ответ без нового запуска агента. Ошибки токена/конфигурации и конфликт polling (`401`, `404`, `409`) завершают процесс с ошибкой. Подтверждение отправки списка и переход `await_delivery → await_selection` атомарны. Устаревшие списки получают `superseded`. Старый выбор без подтверждённой доставки требует повторного показа списка.

## Тесты

Для unit-тестов и проверок с подставной LLM внешние токены не нужны:

```sh
go test ./...
go vet ./...
```

Проверка JavaScript формы без установки Node на хосте:

```sh
make test-web
```

Используется временный контейнер Node с репозиторием только для чтения и без
сети. Тесты запускают настоящий обработчик формы с подставными DOM/HTTP и
проверяют PATCH, версию, конфликт и сохранение ввода. Они не заменяют проверку
внешнего вида и взаимодействия в браузере.

Интеграционные тесты работают **только с отдельной тестовой БД** с именем, заканчивающимся на `_test`, и очищают её таблицы. Не используйте DSN приложения.

```sh
docker compose -f deploy/docker-compose.test.yaml -p expenses-test up -d --wait
test_db_address=$(docker compose -f deploy/docker-compose.test.yaml -p expenses-test port db 5432)
TEST_DATABASE_URL="postgres://postgres:test@${test_db_address}/expenses_test?sslmode=disable" go test -race ./...
docker compose -f deploy/docker-compose.test.yaml -p expenses-test down
```

По умолчанию Docker выбирает свободный порт тестовой БД. Для параллельных окружений используйте разные имена проекта (`-p`); при необходимости задайте конкретный порт через `TEST_DB_PORT`.

Проверяются точные деньги и переполнение, валидация, часовой пояс на границе суток, allowlist и личные чаты, выбор «вторую», несовпадение прежней суммы, недопустимые аргументы LLM, лимит шагов, `429`, отмена контекста, ошибки финального ответа, дедупликация доставки. Регрессионные тесты также проверяют параллельную обработку разных участников, порядок сообщений и сохранение сессии одного участника, повтор пакета после ошибки без повторного вызова агента для завершённых update, отмену обработчиков и совместимость JSON ранее сохранённых сессий; запрет обхода уточнения через latest, сохранение ожидающего изменения, порядок нумерации, постоянные ошибки доставки, предел повторов, `retry_after`, обработку следующего участника и отсутствие секретов в диагностике. Проверяется полная цепочка выбора: сохранение кандидатов, ошибка отправки списка, ранний ответ, успешная повторная доставка, отклонение ответа из старой очереди и применение нового выбора. Также проверяются отмена устаревшего списка, очистка выбора после терминальной ошибки и таймаут API на реальной блокировке строки PostgreSQL. PostgreSQL-тесты проверяют восстановление после коммита и сбоя сохранения сессии, расписание доставки и повторное открытие начальной схемы, а также CRUD, чужие ID, фильтры, пагинацию и общий итог, очистку комментария, сортировку последней созданной записи, конкурентный повтор мутации, истечение сессий, REST-контракт и сохранение данных при повторном открытии.

Ручная приёмка с реальными доступами:

1. От двух разрешённых участников добавьте «кофе 350» и «такси 1200 вчера».
2. Проверьте суммы и даты в панели; примените фильтры.
3. Измените расход в панели, запросите его через бота и проверьте отчёт.
4. Добавьте несколько поездок, отправьте «удали такси», затем «вторую».
5. Убедитесь, что второй участник не видит чужих расходов, а пользователь вне allowlist не получает доступа.
6. Выполните `docker compose --env-file .env -f deploy/docker-compose.yaml restart` и проверьте сохранность расходов.

Тесты агента проверяют аргументы хранилища, права на операции, уточнения, выбор, восстановление и HTTP-контракт LLM-клиента. Подставное хранилище не имитирует SQL и долговременную дедупликацию: эти свойства проверяются отдельно с PostgreSQL.

Тесты с подставной LLM не подтверждают качество конкретной модели. Для повторения живой проверки Telegram/Groq нужны собственные credentials. Ручная приёмка от 19.10.2026 подтвердила создание и изменение расходов, выбор и отмену удаления, изоляцию двух Telegram-аккаунтов, конфликт редактирования в браузере и сохранность после перезапуска.

Состояния доставки хранятся как PostgreSQL ENUM `telegram_update_state`,
определённый в единственной начальной миграции `001_init.sql`. Она создаёт
полную актуальную схему на пустой БД. Уже применённые миграции повторно
не выполняются. Локальная база разработчика ранее обновлена до этой схемы;
обновление промежуточных схем до объединения миграций не поддерживается.

## Ограничения

Одна семья, одна валюта; нет возвратов, авторизации панели, голоса, вложений, экспорта и бюджетов. Telegram рассчитан на один polling-процесс. Долгий LLM-запрос не задерживает других участников уже полученного пакета, но следующий пакет и повтор доставки ждут завершения текущего. HTTP и бот работают в одном процессе с общим завершением при фатальной ошибке. История ограничивается при каждом новом запросе; истёкшие сессии не используются, но физически перезаписываются при следующем обращении. Журнал операций и обработанных update не очищается автоматически. При сетевой неопределённости вокруг `sendMessage` ответ может прийти повторно, но мутация БД защищена от повторного применения.
